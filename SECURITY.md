# Security

This is a portfolio project with a public demo tenant, not a service holding
anyone's money. That changes what is worth reporting, not whether reports are
welcome.

## Reporting

Open a [private security advisory](https://github.com/dnakhoa/obol-ledger/security/advisories/new).
Please do not open a public issue for anything exploitable.

I will acknowledge within a few days. There is no bounty.

## What is in scope

Anything that breaks an invariant the project claims to hold:

- An entry that commits without summing to zero
- Reading or writing another tenant's rows
- A balance that disagrees with the postings behind it
- Forging a webhook signature, or making the dispatcher reach a private address
- Recovering an API key or webhook secret from anything the API returns

## What is out of scope, and why

The deployed demo makes deliberate trade-offs that would be wrong in a real
deployment. They are documented rather than hidden — see
[`docs/comparison.md`](docs/comparison.md).

- **The demo tenant accepts unauthenticated writes** through the dashboard's
  server actions. That is how the deployment is explorable. Posting an entry
  or issuing a key without a credential is the intended behaviour, not a
  finding.
- **Rate limiting is per-instance.** Documented, and fixed in the database
  rather than pretended about.
- **DNS rebinding** against a webhook target. The resolved address is checked,
  but pinning it into the connection is not something Node's `fetch` exposes.
- Missing security headers on the _demo_ deployment, absent a threat model
  that needs them.
- Anything requiring physical access, a compromised developer machine, or
  social engineering.

## What is not a vulnerability

Reports generated by a scanner with no demonstration of impact, and findings
about dependencies with no reachable path from this code.
